Lesson 01 · Human-in-the-loop AI coding

Grill before you build

The highest-leverage move in AI-assisted coding happens before a single line is written: turning the conversation around so the AI interrogates you.

Mission: fewer review rounds, you in control

The problem with prompt-first

As a daily Claude Code user you already know the failure mode: you describe a change ("add offline caching to the trip screen"), the model writes plausible code, and then you spend three rounds correcting it — wrong data shape, wrong edge cases, a term that means something else in your codebase. Each correction is context you should have supplied up front.

When that half-understood code reaches a colleague's PR review, they catch the same gaps — slowly, expensively, in comments. The cost didn't disappear; it moved downstream to the most expensive reviewer.

The shift: context-first

Instead of prompt → code → correct, you run grill → shared understanding → code. You pay the context cost once, deliberately, while it's cheap — not repeatedly in review. This is the whole reason the grill-with-docs skill exists.

The grilling loop

A grilling session inverts the usual dynamic. From the actual installed skill (SKILL.md, your primary source), four mechanics define it:

  1. One question at a time. It walks down each branch of the design tree, resolving dependencies between decisions one by one — and waits for your answer before moving on.
  2. Every question comes with its recommended answer. You're not staring at a blank prompt; you're approving, rejecting, or refining a proposal. Much lower effort, much higher signal.
  3. It explores the codebase instead of asking whenever a question can be answered by reading the code. It won't make you recite what it can verify.
  4. It writes understanding down as it crystallises — sharpening terminology in CONTEXT.md and recording real trade-offs as ADRs, inline, not batched at the end.

You invoke it the same way you'd invoke any skill — point Claude Code at the plan and ask it to grill you with grill-with-docs before writing code. Then your job changes from author to interviewee: answer precisely, correct fuzzy language, and let it dig.

What "with docs" adds

Plain "grill me" is the interrogation loop on its own. grill-with-docs adds a domain layer: it challenges your plan against your project's existing language and recorded decisions. If you say "cancel the booking" but the glossary defines cancellation differently — or your code already does it another way — it surfaces the contradiction on the spot. The artefact that survives is a tightened CONTEXT.md glossary your whole team can read.

CONTEXT.md is a glossary and nothing else — no implementation details, no spec. That constraint is what keeps it valuable.

Set the grill up before you run it

Two choices made before the first question decide how good the session can be — and they're two of the most common ways a grill starts handicapped (drawn from AI Hero's writeup on grilling mistakes, cited at the foot of this lesson).

Grill with your strongest model; scope it small

Use a frontier model to grill. Grilling runs on the model's parametric knowledge — the judgement baked into its training — not on your repo. A weaker model gives weaker ideas and tamer questions. Reach for the most capable model (Opus) here; you can drop to something cheaper for implementation, where the knowledge that matters is contextual — your files, your plan, the answers you just gave.

Scope one grill to one change. Too large a scope drags the conversation out of the model's sharp zone — attention frays as the context window fills, well before any hard limit — and broad plans hide high-fidelity questions you can't settle in words yet (Lesson 2). If the plan is big, ask it to break the scope into chunks and grill each one separately.

Your win for today

Run one grill before you build

Take the next real ticket you'd normally just prompt Claude Code to implement. Before writing any code:

  1. Describe the change and the relevant files, then ask Claude Code to run grill-with-docs on the plan and not write code yet.
  2. Answer its questions precisely. When it proposes a recommended answer you disagree with, say why — that's the highest-value signal you can give.
  3. Notice the moment it would normally have guessed wrong. That caught gap is one fewer review comment from a colleague.
  4. Let it update CONTEXT.md. Skim the glossary it produces — is your team's language actually that precise today?
